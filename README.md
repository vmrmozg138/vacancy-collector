# Парсер вакансий

[![tests](https://github.com/vmrmozg138/vacancy-collector/actions/workflows/tests.yml/badge.svg)](https://github.com/vmrmozg138/vacancy-collector/actions/workflows/tests.yml)

Сборщик данных из открытых источников: забирает данные по API и с сайтов, приводит их
к единому виду и складывает в базу так, что повторный запуск не создаёт дублей.
Пакет в коде называется `collector`.

Проект сделан как рабочий инструмент, а не как учебное задание: запускается по расписанию,
пишет логи в файл, умеет работать и с SQLite, и с PostgreSQL, тесты не зависят от сети.

## Что уже работает

| Источник | Тип | Что делает |
|---|---|---|
| **«Работа России»** (`opendata.trudvsem.ru`) | открытое API (JSON, без ключа) | забирает вакансии постранично, ~491 000 записей в базе источника |
| **Википедия** | HTML-страницы | собирает справочник субъектов РФ: тип, федеральный округ, территория, население, административный центр |

## Быстрый старт

Нужен Python 3.11+ и [Poetry](https://python-poetry.org/).

```bash
poetry install                    # создаст .venv рядом с проектом и поставит зависимости
copy .env.example .env            # при необходимости поправить настройки

poetry run python -m collector.cli run --source trudvsem --pages 3 --limit 50
poetry run python -m collector.cli stats
```

Версии зависимостей зафиксированы в `poetry.lock`, поэтому окружение соберётся одинаково
на любой машине: `poetry install` — и всё.

Фильтр по тексту уходит на сторону источника, по региону — применяется у нас:

```bash
poetry run python -m collector.cli run --source trudvsem --pages 2 --text python
poetry run python -m collector.cli run --source trudvsem --pages 5 --region Москва
```

Тесты (без сети, на сохранённых ответах источника):

```bash
poetry run pytest
```

Справочник регионов и отчёт по нему:

```bash
poetry run python -m collector.cli run --source wikipedia-regions   # собрать справочник
poetry run python -m collector.cli districts                        # вакансии по федеральным округам
```

## Как это устроено

```
источник (sources/)  →  конвейер (core/pipeline.py)  →  хранилище (storage/)
   сеть и разбор            оркестрация и лог              база и upsert
```

- **Источник** знает только, как получить данные и как их разобрать. Про базу он не знает ничего.
- **Конвейер** соединяет источник и хранилище, считает статистику и записывает её в журнал запусков.
- **Хранилище** отвечает за запись: одна команда `INSERT ... ON CONFLICT DO UPDATE` на пачку строк.

Такое разделение даёт две вещи: парсеры тестируются на фикстурах без сети,
а хранилище можно проверить на любых подготовленных данных.

### Почему данные не дублируются

У пары «источник + внешний идентификатор вакансии» есть уникальный индекс
(`uq_vacancy_source_external`). Запись идёт через upsert: если вакансия уже есть — обновляются
поля, если нет — вставляется строка. Повторный запуск либо ничего не меняет, либо обновляет
изменившиеся данные, но не размножает их.

### Почему это устойчиво к сбоям

- HTTP-слой делает повторы с нарастающей паузой на 429/5xx и учитывает заголовок `Retry-After`;
- между запросами выдерживается пауза (настройка `COLLECTOR_DELAY`) — не создаём нагрузку
  на чужой сервер;
- одна битая запись источника пропускается, а не роняет весь запуск;
- каждый запуск пишется в таблицу `runs`: сколько скачали, сколько записей добавили и обновили,
  сколько было ошибок.

### Схема данных

- `vacancies` — вакансии; уникальный ключ `(source, external_id)`, поле `raw` хранит исходный JSON,
  `region_key` — нормализованное название региона для связи со справочником;
- `regions` — справочник субъектов РФ: тип, федеральный округ, территория, население, админ. центр;
- `runs` — журнал запусков сборщика;
- `raw_documents` — сырые ответы источников как есть (например, HTML после выполнения JavaScript).

### Справочник регионов: зачем второй источник

Вакансии приходят с названием региона в том виде, как его записал работодатель: «Город Москва»,
«Чувашская Республика - Чувашия». Справочник даёт к каждому региону федеральный округ, территорию
и население, а значит позволяет отвечать на вопросы, которых в исходных данных нет:
сколько вакансий в каждом округе, как они соотносятся с численностью населения.

Сопоставлять названия «в лоб» нельзя, поэтому считается нормализованный ключ
(`core/normalize.py`): нижний регистр, «ё» → «е», выброс служебных слов («город», «республика»,
«область»), скобок, дефисов и тире, сортировка слов. «Город Москва» и «Москва» дают один ключ,
«Республика Алтай» и «Алтайский край» — разные.

**Идеального сопоставления не бывает**, и это видно в отчёте: команда `districts` показывает
отдельно «регион найден в справочнике» и «из них с известным федеральным округом».
Разница возникает честно — например, регион есть в справочнике субъектов, но отсутствует
в списках федеральных округов на странице-источнике. Прятать такие расхождения в отчёте
хуже, чем показать их числом.

### Правила работы с сайтами

- **Сначала API, потом HTML, потом браузер.** У «Работы России» есть официальное API — HTML там
  не нужен. У Википедии API нет для таблиц — читаем страницу. Браузер (выполнение JavaScript)
  подключается последним и только если данные действительно рисуются на клиенте.
- **`robots.txt` проверяется до запроса** (`core/robots.py`): результат кэшируется на домен,
  отказ попадает в лог, а не игнорируется молча. Если файла нет — считаем, что запрета нет,
  но так и пишем в лог: «не смог проверить» и «проверил, разрешено» — разные вещи.
- **Соблюдается `Crawl-delay`**, если сайт его просит, плюс собственная пауза между запросами.
- **Фикстуры обновляются скриптом** `poetry run python -m tools.refresh_fixtures`: он заново
  скачивает страницы, обрезает их до фрагментов и выбрасывает служебную разметку.
  В начале каждой фикстуры указан адрес источника и дата выгрузки.

### Когда нужен браузер (команда `render`)

Решение «подключать браузер или нет» принимается по факту, а не по привычке:

```bash
poetry run python -m collector.cli render \
  --url https://quotes.toscrape.com/js/ \
  --xpath "//div[@class='quote']"
```

Команда показывает три вещи: сколько элементов видно в HTML, который отдал сервер; сколько их
после выполнения JavaScript; и вывод — нужен ли браузер вообще. HTML после рендеринга сохраняется
в `raw_documents`, поэтому разбирать его можно повторно, не запуская браузер заново.

**Браузеры Playwright скачиваются отдельно** и на этой машине лежат в `.pw-browsers` — в папке
проекта, а не в профиле пользователя (в профиль система писать не дала). Путь берётся из
переменной `PLAYWRIGHT_BROWSERS_PATH`, а если её нет — из `.pw-browsers`, если такая папка есть.
Поэтому установка и запуск должны видеть один и тот же путь:

```powershell
$env:PLAYWRIGHT_BROWSERS_PATH = "$PWD\.pw-browsers"
$env:TEMP = "$PWD\.tmp"; $env:TMP = $env:TEMP
poetry run playwright install chromium
```

Проверка, что браузер работает: `poetry run pytest -m integration` (обычный прогон тестов
интеграционные тесты пропускает — они помечены маркером `integration`).

### Если схема базы изменилась

`create_all` создаёт только отсутствующие таблицы и никогда не меняет существующие, поэтому после
добавления поля в модель старая база остаётся без него. При старте выполняется `ensure_schema`:
недостающие колонки и индексы добавляются, а в лог пишется предупреждение, что именно изменилось.
Это облегчённая замена миграциям — обязательные колонки без значения по умолчанию так добавить
нельзя, для них нужен настоящий инструмент миграций (Alembic).

## База данных

По умолчанию проект пишет в SQLite-файл рядом с собой — этого достаточно, чтобы быстро всё
попробовать. Рабочий вариант — PostgreSQL в контейнере:

```bash
docker compose up -d        # поднять базу
docker compose ps           # ждём статус healthy
docker compose down         # остановить (данные останутся в томе)
docker compose down -v      # остановить и стереть данные вместе с томом
```

Затем укажите её в `.env`:

```
COLLECTOR_DB_URL=postgresql+psycopg://collector:collector@localhost:5433/collector
```

**Кода это не касается вообще** — ни одной строки: отличается только строка подключения.
Так и задумано: всё, что знает про базу, лежит в слое `storage`.

Почему порт **5433**, а не привычный 5432: на 5432 слушает локальный PostgreSQL, установленный
в систему, и подключение к `localhost:5432` уходило бы в него, а не в контейнер. Наружу контейнер
отдан на 5433, конфликта нет. Это единственное место в проекте, где мы отступили от стандартного
порта, и причина записана прямо в `docker-compose.yml`.

### Если порт занят: как это выглядит и как проверить

Симптом: контейнер поднялся и честно показывает `healthy`, но подключение падает с «пароль
не прошёл проверку» или «база не найдена». Это значит, что на порту отвечает **кто-то другой** —
healthcheck контейнера проверяет базу внутри контейнера и о конфликте снаружи ничего не знает.

Проверить, кто именно занимает порт:

```powershell
Get-NetTCPConnection -LocalPort 5432 -State Listen | Select-Object LocalAddress, OwningProcess
Get-Service | Where-Object { $_.Name -like '*postgres*' }
docker ps --format "{{.Names}} {{.Ports}}"
```

Порт не «загрязняется» и не требует очистки: он либо кем-то слушается прямо сейчас, либо свободен,
и освобождается сразу при остановке процесса или контейнера. Источников конфликта обычно три:
служба Windows, другой контейнер с тем же публикуемым портом, процесс внутри WSL.

Если на 5432 уже работает локальный PostgreSQL, разумнее сменить публикуемый порт контейнера,
чем останавливать рабочий сервер: в `docker-compose.yml` это запись `"5433:5432"` — снаружи 5433,
внутри контейнера по-прежнему стандартный 5432. И не забывайте про локаль сервера: ответ
**на другом языке**, чем ожидалось, — верный признак, что вы говорите не с тем сервером.

Что проверить после первого запуска:

```bash
poetry run python -m collector.cli --db "postgresql+psycopg://collector:collector@localhost:5433/collector" stats
```

Должно показать то же самое, что на SQLite: количество вакансий, топ регионов и журнал запусков.

## Запуск по расписанию

Расписания в коде нет намеренно: конвейер отвечает на вопрос «что делать за один запуск»,
а «когда запускать» — задача системы. Поэтому сбор вешается на штатный планировщик Windows:

```powershell
# каждый день в 8:30
schtasks /Create /TN "collector-trudvsem" /SC DAILY /ST 08:30 ^
  /TR "cmd /c cd /d C:\путь\к\collector && py -m poetry run python -m collector.cli run --source trudvsem --pages 5"
```

Проверить и запустить вручную:

```powershell
schtasks /Query /TN "collector-trudvsem" /V /FO LIST
schtasks /Run /TN "collector-trudvsem"
```

Почему так, а не циклом внутри приложения: планировщик сам переживает перезагрузку, ведёт журнал
задач, умеет догонять пропущенный запуск и не требует держать процесс в памяти. А раз каждый
прогон пишет итог в таблицу `runs` и возвращает код возврата (0 — успех, 1 — ошибка), сбой видно
и в планировщике, и в базе.

## Настройки (`.env`)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `COLLECTOR_DB_URL` | `sqlite:///collector.db` | строка подключения: SQLite или PostgreSQL (см. раздел про базу) |
| `COLLECTOR_USER_AGENT` | `OpenDataCollector/0.1 (+github)` | представление клиента с контактом |
| `COLLECTOR_TIMEOUT` | `30` | таймаут запроса, секунды |
| `COLLECTOR_DELAY` | `0.5` | пауза между запросами |
| `COLLECTOR_MAX_RETRIES` | `4` | число попыток на запрос |
| `COLLECTOR_LOG_FILE` | `collector.log` | файл лога |

## Этика и легальность сбора данных

Правила, которых придерживается проект:

1. **Сначала официальное API.** Если источник отдаёт данные сам — парсить HTML не нужно:
   это и стабильнее, и не нарушает правила сайта.
2. **Соблюдаем `robots.txt` и правила использования.** Там, где сбор запрещён условиями,
   мы данные не собираем — даже если технически это возможно.
3. **Представляемся.** В `User-Agent` указан клиент и контакт: администратор сайта может
   связаться, а не блокировать трафик молча.
4. **Не создаём нагрузку.** Паузы между запросами, разумное число страниц, никакого
   параллельного «долбления».
5. **Обход защиты — не решение.** Капча и антибот-защита на сайтах вроде Avito, ФССП или ЕФРСБ
   означают, что данные предоставляются иначе: через официальный API, договор, выгрузку
   или запрос в поддержку. Это дешевле в поддержке и не создаёт юридических рисков.
6. **Чужие персональные данные не публикуем.** Вместе с вакансиями источник отдаёт контакты
   работодателей (почты, телефоны, имена контактных лиц). В репозиторий такие данные не попадают:
   тестовые фикстуры обезличиваются скриптом `python -m tools.sanitize_fixtures`, а база и логи
   исключены через `.gitignore`.

## Выгрузка вакансий (и как этим пользоваться в поиске работы)

Собранные данные нужны не сами по себе, а чтобы по ним искать. Команда `export` отбирает
вакансии и пишет CSV, который открывается в Excel:

```bash
poetry run python -m collector.cli export --district "Сибирский" --salary-min 150000
poetry run python -m collector.cli export --region Москва --text python --out exports/python.csv
poetry run python -m collector.cli export --remote --limit 500
```

Фильтры:

| Ключ | Что делает |
|---|---|
| `--text` | подстрока в названии, компании или регионе |
| `--region` | регион: подстрока или точное название («Город Москва» найдётся и по «Москва») |
| `--district` | федеральный округ из справочника («Сибирский», «Центральный») |
| `--salary-min` | зарплата не ниже указанной (сравнение по верхней границе вакансии) |
| `--remote` | вакансии, где в описании есть слова про удалёнку или дистанционную работу |
| `--limit` | сколько строк выгрузить (по умолчанию 200) |
| `--out` | путь к файлу (по умолчанию `exports/vacancies.csv`) |

Две честные оговорки. **Первая:** признак удалёнки — это поиск слов «удал…» и «дистанц…»
в исходном описании вакансии, потому что отдельного поля источник не отдаёт. Надёжнее искать
удалёнку сразу на стороне источника: `--text "python удалённо"` при сборе, там это полнотекстовый
поиск по вакансии (проверено: «удалённо» даёт около 5,5 тыс. вакансий по стране).
**Вторая:** файл пишется с разделителем «точка с запятой» и в UTF-8 с BOM — так русский Excel
открывает его без настройки импорта.

## Запуск в контейнере

Сборщик тоже умеет работать в контейнере: база — отдельный сервис, приложение — отдельный профиль.

```bash
docker compose --profile app build
docker compose --profile app run --rm app run --source trudvsem --pages 2
docker compose --profile app run --rm app export --district "Сибирский"
```

Внутри сети адрес базы — `postgres:5432`, поэтому строка подключения в `docker-compose.yml`
отличается от той, что в `.env`. Выгрузки примонтированы на хост в `exports/`.

Браузер в образ не включён: Chromium с зависимостями весит сотни мегабайт, а нужен только
команде `render`. Если она понадобится в контейнере, образ нужно расширять отдельно —
это осознанный выбор, а не забывчивость.

## Антибот и легальность: где проходит граница

Этот раздел — про решения, которые принимаются до кода, и он же самый частый вопрос на интервью
для вакансий, связанных со сбором данных.

**Порядок выбора источника — от дешёвого и законного к дорогому:**

1. **Официальный API.** Данные отдают сами, правила описаны, лимиты известны.
   Так устроен источник этого проекта: «Работа России» даёт открытый API, и никакой парсинг
   HTML там не нужен вообще.
2. **Открытая страница с разрешённым доступом.** Если API нет, читаем HTML: проверяем
   `robots.txt`, представляемся в `User-Agent`, держим паузу, не тянем лишние страницы.
   Так собран справочник регионов.
3. **Браузер.** Только если данные действительно рисует JavaScript, и это подтверждено фактом
   (команда `render`): 0 элементов в HTML и 10 после рендеринга. Браузер медленный, тяжёлый
   и легко ломается — платить этим за то, что уже лежит в HTML, незачем.

**Чего мы не делаем.** Не обходим капчу, не подделываем поведение человека, не ломаем
ограничения доступа, не собираем данные там, где это запрещено условиями использования.

**Как это выглядит на практике.** У крупных площадок объявлений (например, Avito) автоматический
сбор запрещён правилами, а страницы защищены: данные рисует JavaScript, запросы ограничивают
по IP, есть капча. Технически это обходится — и именно поэтому такие заказы существуют.
Но цена обхода не в коде: сбор нарушает договор с площадкой, ломается при любом изменении защиты,
требует постоянной поддержки и создаёт риск блокировок и претензий. Через месяц такой парсер
приходится переписывать, а через год — объясняться.

У государственных реестров, важных для работы с долгами (банк данных исполнительных производств
ФССП, реестр сведений о банкротстве), доступ устроен иначе: официальный сайт с капчей и поиском
вручную, а для организаций существуют отдельные официальные каналы — соглашения, выгрузки,
платные подписки. Правильный путь — идти в эти каналы, а не эмулировать человека в браузере.

**Что делать вместо обхода**, по убыванию полезности:

- найти официальный API или выгрузку (у большинства крупных источников они есть);
- договориться о партнёрском доступе — площадкам часто выгоднее дать API, чем воевать с парсерами;
- использовать открытые государственные данные (для регионов, справочников, статистики);
- если данные нужны разово — запросить их у владельца или купить готовый набор.

**Как это встроено в проект:**

- `robots.txt` проверяется до запроса, результат кэшируется, отказ попадает в лог (`core/robots.py`);
- в `User-Agent` указан клиент и контакт — администратор сайта может связаться, а не блокировать молча;
- пауза между запросами и ограничение числа страниц (`COLLECTOR_DELAY`, `--pages`);
- команда `render` заменяет спор «нужен ли браузер» измерением;
- вместе с вакансиями источник отдаёт контакты работодателей — в репозиторий они не попадают,
  тестовые фикстуры обезличиваются, база и логи исключены через `.gitignore`.
